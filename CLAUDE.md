# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A VS Code extension ("Workspace List") that maintains a curated list of workspaces (folders / `.code-workspace` files) with user-editable metadata (description, tags, color, favourite files), shown in a dedicated activity bar view. Full design spec is in `SPEC.md` — read it for intended behavior before implementing features not yet present in the code.

## Commands

- `npm run compile` — type-check only (`tsc --noEmit`), no output emitted. Use this to verify changes.
- `npm run build` / `npm run package` — production bundle via esbuild to `dist/extension.js`.
- `npm run watch` — esbuild in watch mode for iterative development.
- No test suite or linter is currently configured.
- To try the extension: open this folder in VS Code and press F5 (Run Extension) to launch an Extension Development Host, or package with `npx vsce package` and install the `.vsix` via "Extensions: Install from VSIX...".
- **Bump `version` in `package.json` before every `vsce package`** — installed VSIX extensions are frozen at package time, and reusing the same filename/version makes it impossible to tell whether a reinstalled build is actually fresh.
- **Every push to GitHub must bump the version and publish a matching GitHub Release** (`git tag vX.Y.Z && git push origin vX.Y.Z`, then `gh release create vX.Y.Z <vsix> --title vX.Y.Z --notes "..."`) — `src/update.ts`'s self-update check compares against the latest *Release*, not commits or tags alone; pushing commits without a release makes "Check for Updates" report the extension is current when it isn't (hit this after v0.1.33: commit was pushed but no release existed, so the update check kept reporting current).
- **Build the `.vsix` locally** (`npm run package && npx vsce package`) and attach that exact file to the GitHub Release as an asset — don't rely on GitHub's auto-generated source archives for distribution.

## Architecture

Entry point is `src/extension.ts`, bundled by esbuild (`esbuild.js`) with `vscode` as the only external — everything else is bundled into a single `dist/extension.js` CJS file (`platform: node`).

Data flow is a simple store → tree/webview pattern:

- **`src/types.ts`** — `WorkspaceEntry`/`Group`/`FavouriteFile`/`WorkspaceListData` shape and the on-disk JSON schema (`version: 2`; `version: 1` files, which had no `groups` array, are migrated in-memory on load — see `store.ts`). Groups can nest via `Group.parentId`; a `WorkspaceEntry.groupId` (or a `Group.parentId`) of `undefined` means "at tree root".
- **`src/store.ts`** (`WorkspaceStore`) — sole owner of persistence. Reads/writes a single JSON file (`workspace-list.json`) shared across *all* VS Code profiles on the machine, resolved via `sharedUserDirUri(context)` (`context.globalStorageUri` walked up two levels to the shared per-installation `User` folder, the same directory `settings.json` lives in — not Settings Sync'd). A legacy per-profile `workspaces.json` is migrated in-place on first load if present (`LEGACY_STORE_FILE`/`migrateLegacyIfPresent`). `watchForExternalChanges()` uses a `RelativePattern`-based `FileSystemWatcher` on that shared file so edits in one profile/window live-propagate to all others without a reload; `suppressNextWatcherEvent` avoids a window re-processing its own write. Writes are serialized through a `writeQueue` promise chain and done atomically (write to `.tmp`, then `rename`). Fires `onDidChange` after every persist; nothing else touches the file directly. Sibling `sortOrder` is scoped per-parent (per `groupId`/`parentId`), not global. `removeGroup` reparents its children (both subgroups and entries) up to the removed group's own parent rather than deleting them. `isDescendantOrSelf` guards against creating cycles when reparenting a group via drag-and-drop.
- **`src/treeProvider.ts`** (`WorkspaceTreeProvider`) — `TreeDataProvider` *and* `TreeDragAndDropController` for the `workspaceList.view` view. Three node kinds: `GroupNode` (organizational only — no `command`, so clicking/expanding never opens anything), `WorkspaceNode` (has an `item.command` — `workspaceList.entryClicked` — fired on *every* click, including a repeat click on an already-selected row, since `onDidChangeSelection` alone doesn't fire in that case; extension.ts's handler does the double-click timing/dispatch), and `FavouriteFileNode` (only actionable — i.e. clickable to open — when their parent workspace matches `vscode.workspace.workspaceFolders`/`workspaceFile` of the *currently open* window). `getChildren`/`buildLevel` walks one group level at a time via `store.getGroupsByParent`/`getEntriesByGroup`, mixing subgroups and entries at each level. `getParent` is implemented (required for VS Code's `reveal()`/some drag-drop scenarios) by walking `groupId`/`parentId` back through the store. The filter (`setFilter`, substring match on name/description/tags) is applied per-level and a group is kept if it or any descendant matches (`subtreeHasMatch`). Icons: groups use custom-drawn SVG data URIs (`groupIconOpen`/`groupIconClosed`, not codicons — `ThemeIcon('folder')`/`'root-folder'`/`'folder-opened'` looked visually near-identical in practice) tinted by the group's `color`, defaulting to yellow (`DEFAULT_GROUP_COLOR`) rather than gray so groups read as folders at a glance; which shape is used tracks each group's *live* expand/collapse state via `collapsedGroupIds` (a `Set<string>` on the provider, updated from `treeView.onDidExpandElement`/`onDidCollapseElement` in `extension.ts` — this state is session-only, not persisted). Plain OS folder entries use a custom SVG open-folder shape (`osFolderIcon`) tinted by the entry's `color` (default gray). `.code-workspace` project entries use the built-in `ThemeIcon('repo')` tinted via `new vscode.ThemeColor('charts.yellow')` — a real theme-color id, since `ThemeIcon` can't take arbitrary hex the way the custom SVGs can, so per-entry `color` is *not* applied to project entries. The hex-only limitation on `ThemeIcon` is also why label *text* color was ruled out entirely — only icons can be tinted.
  - **Drag-and-drop** (`handleDrag`/`handleDrop`): VS Code's `TreeDragAndDropController.handleDrop` only ever receives the drop *target* node, with no before/after position — so the meaning of a drop is inferred from what kind of node it lands on. Dropping onto a **group's own row** reparents the dragged item(s) into that group, appended at the end (`store.appendToLevel`). Dropping onto a **workspace entry** (a leaf, can't contain children) instead reorders the dragged item to sit immediately *after* that entry within its parent group (`store.reorderWithinLevel`) — this is the only way to change sequence, since there's no "insert before" affordance. Dropping on empty space below the tree appends to the root level. Dropping a group onto its own descendant is rejected (`store.isDescendantOrSelf`).
- **`src/metadataEditor.ts`** — one `WebviewPanel` per entry *or* group (a single reusable `entryPanel` for workspace entries — switching entries rebinds it in place via `loadEntryIntoPanel` rather than opening a new panel — plus a `groupPanels` map keyed by group id). The same `renderHtml` is shared between `openMetadataEditor` (workspace entries) and `openGroupMetadataEditor` (groups); the favourite-files section is conditionally omitted for groups by passing `favouriteFiles: undefined`. Color is picked via a native `<input type="color">` (hex, e.g. `#ff8800`) rather than typed VS Code theme-color ids. Strict CSP with nonce'd script, no external resources. All persistence and file-picking happens extension-host-side; the webview only sends `save` and `pickFavouriteFile` messages via `postMessage`. HTML is built manually (no templating library) — keep `escapeHtml` applied to any interpolated user data. `refreshEntryPanelIfShowing(store, entryId)` is exported so other code (e.g. a tree-level command) can push a store change into an already-open entry panel without going through the webview's own message flow.
- **`src/update.ts`** — self-update mechanism for this VSIX-distributed (non-Marketplace) extension, using GitHub Releases as the source (`REPO = 'mirekkl/vscext_workspace-list'`, public repo required for unauthenticated `api.github.com` access). `checkForUpdateOnStartup` throttles to once per 24h via `context.globalState`; `createUpdateStatusBarItem` shows/hides a status bar item and sets the `workspaceList.updateAvailable` context key that gates the title-bar update button in `package.json`. Treat this as fragile if the repo visibility or release-asset naming changes.
- **"New Group"** uses a pre-filled (`value: 'New Group'`, pre-selected) `showInputBox` quick-input row, not a modal. VS Code's `TreeView` API has no public hook for genuine in-row inline-textbox editing of custom tree items (that's hardcoded to the native Explorer/`FileSystemProvider` rename flow) — the quick-input is the closest achievable equivalent; don't attempt to build a "real" inline editor here, it isn't exposed by the API.
- **`src/extension.ts`** — wires everything together in `activate()`: constructs the store, tree view (with `dragAndDropController: treeProvider`), and registers all `workspaceList.*` commands (add, addCurrent, importRecent, refresh, filter/clearFilter, entryClicked, openWorkspace, editMetadata, removeWorkspace, addFavouriteFile, openFavouriteFile, plus group commands: addGroup, editGroupMetadata, removeGroup, moveToGroup). Command args often arrive as either a raw `WorkspaceEntry` or a `WorkspaceNode`/`GroupNode` (when invoked from a tree context-menu vs. programmatically) — see the `arg instanceof WorkspaceNode` pattern. Entries added via `+`, "Add Current Workspace", or "Import from Recently Opened" are revealed/selected afterward via `treeView.reveal(new WorkspaceNode(entry), {select:true, focus:true})`. `treeView.onDidExpandElement`/`onDidCollapseElement` are subscribed here to feed `treeProvider.setGroupCollapsed`, driving the group open/closed icon (see treeProvider.ts entry above).
  - **`workspaceList.addFavouriteFile`** — lets a favourite file be added directly from a workspace entry's tree row (inline icon + context menu), not only from inside the metadata editor. Reuses the same `showOpenDialog` pattern as the editor's own `pickFavouriteFile` message handler, persists via `store.update`, then calls `refreshEntryPanelIfShowing` so an already-open metadata panel for that entry reflects the addition immediately.
  - **`workspaceList.addWorkspace`** ("+" button): a single `showOpenDialog` filtered to `*.code-workspace`. Windows' native file-open dialog cannot combine `canSelectFolders: true` and `canSelectFiles: true` in one call — confirmed empirically (setting both silently collapses to a folder-only "Select Folder" dialog that never lists files, filter or no filter). So folders are added by typing/pasting the folder path into the dialog's filename box instead (Windows accepts a typed path even in file-only mode); the actual picked type is determined via `vscode.workspace.fs.stat()`, not trusted from the file extension. Don't re-attempt a combined folder+file dialog — it doesn't work on Windows.

Opening a workspace always uses `vscode.openFolder` with `forceNewWindow: true` — this extension never reuses the current window. Groups are strictly organizational: they never trigger `openFolder` or any workspace switch, only expand/collapse. "Import from Recently Opened" relies on the internal, unstable `_workbench.getRecentlyOpened` command since VS Code has no public API for this; treat that command as fragile across VS Code versions.

All contribution points (commands, views, menus) are declared in `package.json` under `contributes` — when adding a command, it must be registered both there and in `extension.ts`.
